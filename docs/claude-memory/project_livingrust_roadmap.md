## Feature areas (status as of 2026-08-09 session)

- **Movement/navigation** - largest area of active work. Native Gen2 `RustNavMeshAgent` (same component real `scientist2` NPCs use) now drives both `/lr.follow` and the loot task's walk-to-container movement, hybrid with the older hand-built local-stepping engine as fallback (ladder climbing stays hand-built-only, native ladder support unverified). Stuck-recovery escalation (wiggle → navmesh nudge → emergency teleport, teleport now tries last-known-good position first) paced with real reassess pauses so it doesn't read as instant/glitchy. Monument-relative self-learning avoid-zone system exists (confirmed bad pockets, never blacklists a whole monument). Known open gaps: junkpile truck-bed/vehicle-bed loot needs a vault-type movement that doesn't exist yet (parked, low priority unless it proves common); water/ocean crossing behavior for native movement is untested; awning/doorway prop colliders (`awning_600x300*`, `tent_tunnel_branch_doorway`) are a confirmed recurring local-stepping misjudgment (repeat offenders, not yet root-caused/fixed at the geometry level). Horse avoidance added (2026-08-09, `IsBlockedByHorse` in `LivingRust.Commands.cs`) after a live report of a bot climbing onto and getting stuck standing on top of a `RidableHorse` (`RidableHorse : BaseVehicle` shares the same Vehicle World/Vehicle Detailed layers the obstacle mask already treats as solid steppable terrain) - now treated as a hard obstacle to route around, same as another player/bot, both in the main step-blocked check and the sidestep-candidate check. **New open item, parked (2026-08-10)**: a bot (GhostBoomer) ended up dead on top of a warehouse-monument rooftop with no real ladder/staircase access (confirmed via screenshot - forklift, stacked wooden pallets, AC units right at its landing spot, nothing resembling authored access). Two leading theories, not yet confirmed: (1) hand-built local-stepping's step-up check (`TryGetNextStep`/`MaxClimbSpeed`) has no concept of "authored staircase" vs. "stackable prop" - mechanically identical to the real player exploit of climbing stacked pallets/forklifts to reach unintended rooftops, and GhostBoomer's log was full of "native movement never got a usable path... falling back to hand-built" throughout its journey, consistent with spending real time on the exploitable engine; (2) emergency-teleport stuck-recovery uses `NavMesh.SamplePosition`, which only checks "is there baked navmesh nearby," not "is there an actual walkable connection from here" - if the roof has any orphaned/unreachable-by-design navmesh coverage, a teleport recovery could drop a bot straight there with no climbing at all. Available log data (sparse WARNING-level position snapshots only, verbose was off for large stretches) wasn't fine-grained enough to distinguish which actually happened - needs a real single-bot trace (`/lr.debug.trace`/`/lr.debug.tracenpc`) captured live next time a bot heads toward a similar structure, to see the exact tick where it transitions from ground level to rooftop and which movement engine was active at that moment.
- **Combat - Phase 1 shipped 2026-08-11 (reactive ranged combat)**: `LivingRust.Combat.cs`, triggered by a new `OnEntityTakeDamage` hook. Deliberately built from scratch rather than porting `Scientist2FSM`/`NpcShootingComponent` - confirmed via decompile that `NpcShootingComponent` creates its weapon directly (bypassing `player.inventory`/belt entirely), the exact ammo/inventory disconnect this project can't afford. Real, working pieces: `BaseProjectile.ServerUse(HeldEntityServerUseParams)` with a computed `originOverride` (a `Matrix4x4.TRS` toward the target's eyes, `useOwnerForward` forced off) for correct hit-scan; real inventory-aware reload via `BaseProjectile.ServerTryReload(ownerPlayer.inventory)` (confirmed live: ammo genuinely depletes and reloads from the survivor's own inventory, the actual unknown this phase existed to answer); fixed-rule disengage (attacker dead/gone/out of 60m range, or own health ≤25) that resumes whatever task was interrupted. Scope deliberately narrow, explicitly deferred: bows/crossbows/grenades/melee-vs-players, proactive on-sight detection (reactive-to-being-shot only), personality-driven fight-or-flee (fixed rule only, no Personality system exists yet).
- **Combat - visible-facing bug, root-caused and fixed via a full redesign (Phase 1b, 2026-08-11)**: real, deep structural finding via decompile - a real player's visible body/head rotation is ONLY ever broadcast to other clients through `NetworkPositionTick` (`BasePlayer.ServerFinalizePlayers`/`GatherPlayersToFinalize`), which only populates for players that just sent a real `PlayerTick` RPC - something a disconnected bot can never send. Even Rust's OWN native "bot" concept (`BasePlayer.IsBot`) has this same limitation (confirmed: vanilla bots are never added to `PlayerCache` either, since that only happens via `PlayerInit(Connection)`) - `NPCPlayer` sidesteps it entirely by using a different sync model. Manually setting `transform.rotation`/`viewAngles`/`eyes.NetworkUpdate` is server-side-correct but has no channel to reach an observer's screen while the bot stands still - confirmed live (a trace showed `facing_deg` genuinely changing at times, contradicting a purely-server report of "not working," matching Lucas's own read: "the server might be thinking it's correct... this is purely client side"). Real POSITION changes, by contrast, ARE proven to visibly broadcast (every other movement system in this project relies on it and works) - almost certainly because the client's own character model infers orientation from observed movement, not from an explicit networked rotation value. First fix attempt (a bespoke circle-strafe, `CombatStrafe`) worked but was untested new movement code. Lucas proposed something better: don't invent new movement, reuse `StartFollowing` (`LivingRust.Commands.cs`, the same engine `/lr.follow` already uses, mature and already proven to visibly work) as combat's movement engine, with two small enhancements - an optional `stopDistance` parameter (default preserves `/lr.follow` unchanged, combat passes a weapon-tier-dependent engagement range: shotgun 8m/pistol 15m/SMG 20m/rifle 35m) and removing a `!target.IsConnected` exit check (so bot-vs-bot attackers, which `OnEntityTakeDamage` already supports, are followable too - a strict superset of prior behavior, a real player target is always connected anyway). `StartCombat` now calls `StartFollowing` once instead of the strafe; the old NavMeshAgent-disable hack (needed only to stop the agent fighting the manual rotation trick) was removed entirely since `StartFollowing` manages that component itself as part of normal native movement. `EndCombat` now also calls `CancelActiveMovement` to cleanly stop the follow behavior on disengage (nothing did before). **Explicit architecture decision, Lucas's own framing**: combat stays a fully separate reaction/trigger system ("I got shot, react!"), not folded into "the follow task" - it just reuses `StartFollowing` as a shared movement PRIMITIVE, the same way `StartWalkingWithRecovery`/`ApplyMovementStep` are already shared across loot-walking/road-following/monument routes (genuinely different features, one movement engine underneath).
- **New idea, roadmap only per explicit request (2026-08-11) - "react to X event" as the general shape of future reactive behavior**: while designing the visible-facing fix, Lucas proposed building on "look toward where the shot came from, seek LOS, lock on" into a much bigger vision - a bot that reacts to being attacked with real tactical decision-making: flank, retreat, hunker down behind barricades, self-medicate/heal, or wait for backup, not just "walk into range and shoot." Explicitly recognized by both Lucas and Claude as squarely inside the **Personality**/decision-autonomy territory already flagged as the single biggest deferred piece of this whole project (see those roadmap entries) - deliberately NOT scoped or built now, kept out of Phase 1b on purpose to keep that redesign linear. The right shape for whenever this gets picked up: a general "reaction to a world event" framework (being shot is one event; others could include spotting a threat, an ally dying nearby, running low on health/ammo) that consults Personality traits to pick a response, rather than one hardcoded reaction per event type - consistent with the existing Personality entry's own "continuous traits producing behavior, not a fixed enum" design principle.
- **Combat, pre-2026-08-11 note (superseded)**: an earlier research pass into porting `Scientist2FSM`'s flank/retreat/chase/cover decision logic onto real `BasePlayer` bots found it "largely portable" (generic `EntityComponent<BaseEntity>`-based components) - still true for the FSM's tactical states specifically, but NOT for weapon-handling (see Phase 1's own entry above - `NpcShootingComponent` was confirmed the wrong pattern for ammo/inventory reasons) NOR for movement/facing (see Phase 1b's own entry - Scientist2FSM-driven NPCs aren't `BasePlayer` at all, so they never hit this project's specific rotation-broadcast problem in the first place; nothing to port for that piece). If/when the flank/retreat/cover tactical states get built, the FSM's state-graph shape may still be worth referencing, but the weapon/movement pieces are now confirmed to need this project's own real-inventory/real-BasePlayer-specific approach instead.
- **Needs (hunger/thirst/fatigue)** - deliberately NOT a real metabolism-tracking system, per explicit Lucas framing (2026-08-09): "it really isn't a MASSIVE component of rust gameplay, it is just a side thing." Instead, `ConsumeFoodImmediately` (`LivingRust.Looting.cs`) eats any `ItemCategory.Food` item the instant it enters inventory (same trigger as the other loot-success hooks), using the real `ItemModConsume.CanDoAction`/`DoAction` client-consume-button mechanism (confirmed via decompiling `BasePlayer.SV_Drink`'s identical pattern) - genuine metabolism effects apply, `CanDoAction` naturally stops it once `player.metabolism.CanConsume()` says the survivor's already full. No hunger-triggered "go find food" behavior exists (nor is it planned) - this is purely reactive, on-pickup consumption. Thirst/water still fully unaddressed.
- **Looting** - solid shape: task-driven (`TaskType.LootForResources`, still manually triggered via `/lr.debug.settask` - no autonomous need-based trigger yet), container destruction (real damage via actual tool stats) and direct-open both working, real proximity check now enforced (`LootInteractionRange`, added after a bug let a bot loot 10-15m away through a wall), retry-after-N-other-successes for containers that failed once (one retry only, then permanent skip). Loot search is deliberately NOT monument-seeking (plain radius scan) - monument-prioritized looting isn't built. Swing cadence (2026-08-09) now gated on the actually-equipped tool's own real `BaseMelee.HasAttackCooldown()` (per-weapon `repeatDelay`, read at runtime) instead of a flat 1s tick, so hit rate matches "hold click, animation, connect, reset, click again" per real tool instead of hitting every tool at the same fixed pace. Container-approach-angle recovery (2026-08-09, `StartAttackingContainerWithReposition`): when a survivor has already arrived at a container but can't get line-of-sight/real melee range on it (bad approach angle, not physically stuck), it now sidesteps laterally (`ContainerRepositionLateralOffsets`, ±3m/±5m) plus a small step toward the container, up to 4 tries, before giving up - deliberately does NOT fall through to the wiggle/navmesh-nudge/emergency-teleport chain (`EscalateStuckRecovery`, used only for the earlier "can't even walk there" failure mode), since Lucas was explicit this case is "not physically stuck, the container's just genuinely out of reach from any angle" once reposition attempts are exhausted. **Known open issue, explicitly flagged by Lucas 2026-08-09 as "might be ok to skip" pending more observation**: ghost-looting from a distance is still happening even with `LootInteractionRange` (3f) and `HasLineOfSight` in place - likely because 3f is well beyond a real melee weapon's actual reach (`BaseMelee.maxDistance` 1.5f default, `AttackEntity.effectiveRange` 1f, both read at runtime, not this project's own constant), so the bot can land line-of-sight hits/loot from farther than any real player's swing would ever connect. Not yet fixed - watch how it plays out against other monument-default container placements before deciding whether to tighten `LootInteractionRange` toward the tool's real reach. Barrel/container approach standoff (2026-08-09) tightened from 0.6f to `ContainerApproachStandoffDistance` (0.25f) after a live report the bot stood ~0.5m too far back - real melee reach doesn't need that much padding. Junkpile_j's real stuck-duration bug (2026-08-09) fixed: added `RepathFailureGiveUpTicks` (~3s of the real path calculation failing identically in a row) as a fast, direct give-up signal, independent of the older distance-progress heuristic (`WalkGiveUpTicks`/`WalkMinProgressDistance`) that a genuinely-unreachable-but-circling target could fool for 80+ real seconds (confirmed via a live trace: ~1,750 consecutive repath-failed ticks near junkpile_j before the old heuristic finally caught it). Vehicle/deployable fuel tanks (`IsVehicleFuelStorage`, matches "fuelstorage"/"fuel_storage" shortname substrings) excluded from the loot-container search entirely (2026-08-09) after a live report the bot was treating one as lootable world loot. Corpse looting added (2026-08-09): `TryFindNearestLootableCorpse` (`NavigationManager.cs`) + `LootCorpseAndContinue` (`LivingRust.Looting.cs`) - real "rewarded for a kill" behaviour for player/scientist-NPC/animal corpses alike. Paced to `CorpseLootPerItemDelay` (0.2s per item, Lucas's own explicit "let's start there and see how we go" starting value, not yet tuned) rather than an instant transfer-all, matching real auto-loot's own per-item latency. Dropped-bag looting added (2026-08-09): `TryFindNearestDroppedItemContainer` (`NavigationManager.cs`) + `LootDroppedItemContainerAndContinue` (`LivingRust.Looting.cs`) - what a destroyed/despawned body (fire, explosives, or a corpse's own timer) converts into (`DroppedItemContainer : BaseCombatEntity`, real prefab `item_drop_backpack` - a fourth distinct class hierarchy from `StorageContainer`/`LootableCorpse`/`DroppedItem`). `ContinueLootTask` now searches all three (container/corpse/bag) every cycle and picks whichever's actually closest. Shares the same paced per-item loot logic as corpses via a new `LootMultiContainerEntityAndContinue` helper (both `LootCorpseAndContinue` and this now call it) - a corpse and a bag differ in entity type but loot identically. Corpses are a genuinely separate class hierarchy from containers (`LootableCorpse : BaseCorpse : BaseCombatEntity`, not `StorageContainer`), so this needed its own search/loot path - `ContinueLootTask` now searches both every cycle and picks whichever's actually closer. Shares the same post-pickup hooks (equip/armor/food/belt/tidy) as ordinary containers via a new shared `OnLootObtained` helper (also de-duplicated the two pre-existing container call sites). Ground-material awareness: confirmed (2026-08-09) the bot has ZERO physic-material/terrain-texture surface-type understanding beyond a binary `IsWater` check - but the concrete use case that came up (road-following search escalation, below) turned out not to need it at all, since real Rust roads are available as clean spline geometry instead. Road-following loot-search escalation (2026-08-09, `EscalateSearchAlongRoad` + `NavigationManager.TryFindNearestRoadPoint`): once a plain radius scan finds nothing, rather than giving up immediately, the bot now finds the nearest point on a real road spline (`TerrainMeta.Path.Roads` - marked `internal` in Assembly-CSharp but confirmed accessible from this plugin via a live build test) and walks further along it (cumulative hops, Lucas's own example: 10/20/30/40m, capped via `state.RoadFollowAttempts`) before conceding for real. Deliberately a soft heuristic, not a hard constraint - the normal radius scan still runs at every new point and can find loot anywhere, on or off the road; this only decides where to walk next once the immediate area is already empty. Real Rust loot (barrels, junkpiles) spawns disproportionately along roads/paths, so this is a genuine "where would I actually find more" direction-finding pass, not an arbitrary wander. Lucas confirmed this premise visually (2026-08-09, screenshot of a junkpile cluster sitting right off a road shoulder) and flagged `RoadSearchDetectionRadius` (60f)/`RoadFollowDistances` (10/20/30/40m) as likely too small once real gaps between clusters are observed - explicitly deferred ("let's just see how we go") rather than changed blind; revisit these two constants first if road-following keeps giving up before reaching the next real cluster. Dropped world items (2026-08-09 question): confirmed the bot ALSO can't see/pick these up - real dropped items are `DroppedItem : WorldItem`, a third class hierarchy entirely separate from both `StorageContainer` and `LootableCorpse` (its own dropped torch included). Not built - same shape of gap as corpses were, flagged but not yet requested. `vehicle_parts` crate (real shortname, confirmed live) now excluded from the loot search entirely (`IsVehiclePartsContainer`) - a plain exclusion, not an area-avoid, per explicit request. Water bottles (`smallwaterbottle`, also real `ItemCategory.Food`) get their own `DrinkWaterBottles` pass, separate from the generic food loop: drunk via the same real `ItemModConsume` action (free drink animation via its own `SignalBroadcast(Signal.Gesture, eatGesture)`), then the now-empty reusable bottle (real Rust bottles persist/refill rather than being deleted like a food stack) gets dropped for real via `Item.Drop`, same mechanism as the torch.

  - **STILL OPEN as of 2026-08-29 (continued into a second full session) - doors/doorways, by far the most-iterated, least-resolved thing across both sessions.** First-session root-cause chain (ground-probe-hits-doorway-header fix, `CanOpenDoor`/lock-state check, owned-door "ghost hop," close-after-crossing, proactive `ComputeHomeDoorRoute`/`TryGetHomeDoorCrossing`, the busy-flag regression fix) all still stands and is still live, but live retesting kept surfacing NEW, deeper root causes underneath it, in order: (1) `TryGetHomeDoorCrossing`'s near/far point assignment was literally backwards (inside survivor got handed the FAR/outside point as a plain collision-respecting walk target - unreachable through a wall, so it immediately failed onto a raw walk straight at the real destination, racing up the stuck-recovery ladder toward last-resort phase/teleport almost instantly) - this alone fully explained an early "instantly teleports out of the foundation" report. Fixed by swapping the assignment. (2) A survivor approaching a closed, unowned door "side-on" instead of square-on kept oscillating even after opening it - added `ComputeDoorApproachPoint` (squares up on the survivor's own current side, real walk, never crosses the door's plane) plus a widened `DoorOpenDetectionRange` (3f->6f, matching the same `BarricadeAttackDetectionRange` precedent). (3) `StartPhasingToDestination`'s single diagonal leg could climb/dive through a roof/floor if the survivor's Y didn't already match the door's real height - added `StartLevelledPhasing` (vertical-align leg first, stationary horizontally, THEN horizontal leg) for exactly this case. (4) A real ~3.07m base-height corruption (one bad ground-probe sample at a SPECIFIC build's own first foundation, baked into every piece via the shared stacking-offset formula) sent a bot onto the roof of its own door - `GroundHeightMismatchTolerance` tightened 4f->1.5f to actually catch this class of error going forward (can't retroactively fix an already-bad existing base). (5) Lucas's own key reframe: a flat foundation on sloped terrain ALWAYS produces some real height gap between ground and door on whichever edge lands downhill - "hard to tell when they will build it which way," not a bug to eliminate, and "a real player could still make it through by jumping." Added `DoorJumpableHeight` (2m) + reused `StartLevelledPhasing` for the general (non-owned) closed-door approach too, capped to a realistic jump range. (6) Closing the door immediately after a ground-level crossing could still physically shove the survivor UP onto an overhead floor slab (2-story design) if `DoorGhostClearanceDistance` (1.5f) wasn't real clearance of the door's own frame/hinge collider - widened to 2.5f AND added a direct post-close height correction (`DoorCloseHeightCorrectionTolerance`) since the correct height is already known for certain at that exact moment (the door's own real Y), no need to trust a fresh, potentially-wrong ground probe. (7) A completely SEPARATE root cause, not a door bug at all: `EnsureNativeNavAgent`'s `NavMeshAgent.Warp()` call (made unconditional in an earlier fix for a stale-tracking bug) has real, documented Unity behavior of silently snapping to the nearest point genuinely ON the baked static navmesh - and standing inside a survivor's own just-finished base IS exactly such an off-mesh position (the static mesh has no idea player-built floors exist), so the very FIRST native-movement walk after finishing a build could yank a survivor several metres outside with ZERO door-related log line anywhere near it (confirmed via trace: a clean single-tick ~4.66m jump, no "opened door"/"phased through" line before or after). **Swim refinement round 7, 2026-08-15 (later still) - the real architectural cause, found via trace, of the "reverts to standing + teleports" report:** Lucas's framing (swimming back to shore is fine, entering water looks right at first then reverts) pointed at something systemic rather than another edge case. Trace for 'SavageHermit' confirmed it precisely: Y crept progressively DEEPER over an entire 80+ second swim (-1.10 -> -2.16 -> -2.67 -> -3.77...), never stabilizing near the intended -1.10 swim depth at all. Root cause: every swim-Y correction so far only ran INSIDE the native movement "successful step" branch - but Unity's own `NavMeshAgent`, once enabled with a destination, moves the entity's transform continuously every real engine frame, completely independent of this project's own 0.05s tick cadence, and follows the baked navmesh toward the real underwater terrain by default (the same root mechanism as the very first swim bug this session, 'SneakyGoblin81' walking the ocean floor). **New roadmap idea, not yet built, per Lucas's explicit request (2026-08-23) - health-drop-RATE should shape the combat reaction, not just the absolute health number**: current combat only reacts to absolute thresholds (`CombatFleeHealthThreshold`=25 disengage, `CombatHealHealthThreshold`=70 start healing) - it has no concept of HOW FAST health is dropping. **Tactical decision-making system, design scoped + Piece 1 (cover-point discovery) built and live-tested, PARKED per Lucas's own call to revisit later (2026-08-23)** - the first real work toward the long-deferred cover/flee/flank combat item (2026-08-21 priority list, item 2 of 3). Full design conversation, not just the code, worth preserving:

- **Core architecture agreed on**: utility-based SCORING, not a hardcoded state machine - candidate actions (push, hold, flank-left, flank-right, retreat-to-cover, heal) each get scored against real situational inputs on a ~1.5-2s re-evaluation interval (not every combat tick), then picked via WEIGHTED-RANDOM among the top few rather than always the flat best - Lucas's own explicit framing: the bot "needs to appear sentient... it needs to be unpredictable otherwise it counters the living rust appeal." An action simply isn't a candidate at all if its own precondition fails (e.g. no cover found nearby) - this is what makes "caught in the open" fall through naturally to push/hold instead of needing a special-cased fallback branch.
- **Real inputs agreed on, all deliberately fairness-constrained to what a real player could actually know** (directly extending the same fairness principle already applied to the heal-animation-timing fix earlier this session): (1) own health + a rolling health-DROP-RATE (not just instantaneous value) - a fast burst biases toward immediate return-fire/retreat, a slow bleed allows a more considered choice, per the standalone roadmap entry above; (2) cover-point availability (see below); (3) "should I push" - NOT the attacker's real hidden HP (a real player can't see that), but the bot's own legitimately-known cumulative damage dealt to the current attacker THIS engagement (the bot's own combat log, exactly like a real player's) weighed against the attacker's VISIBLY worn armor tier and held weapon (also fair - a real player can see both by looking).
