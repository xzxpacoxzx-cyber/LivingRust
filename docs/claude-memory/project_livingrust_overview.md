`G:\Projects\TemplateProject` is a Rust (game) dedicated server running the Carbon modding framework (C#, .NET Framework 4.8, Harmony-based), building a plugin called **LivingRust**: persistent AI-driven NPC survivors (real connectionless `BasePlayer` instances, not scripted NPCs) that navigate via Rust's baked NavMesh plus custom local-obstacle logic, with planned needs (hunger/thirst/fatigue) and personality-driven decisions.

Key source layout:
- `Navigation\NavigationManager.cs` — pure navigation/pathfinding logic (navmesh wrapping, step-up/down probing, ladder/water/monument/named-structure lookups), no Carbon dependency.
- `Plugin\LivingRust.Commands.cs` — orchestration: walk/follow/climb tick loops, `ClimbState`/`AdvanceClimb`, sidestep logic, `SpawnSurvivor`.
- `Plugin\LivingRust.Debug.cs` — `/lr.debug.*` diagnostic commands (look, nearby, trace CSV logger, claimbag, giveitem). Bots never appear in Rust's native `activePlayerList`/`bots` lookup structures reliably (only populated by real client connection or the sleep/wake cycle respectively), so any admin tool needing to target a specific bot must resolve it through LivingRust's own `Survivor`/`Character` roster, not Rust's native `BasePlayer.Find()` — established pattern, reuse it for future debug commands.
- `Plugin\LivingRust.MonumentRoutes.cs` — authored fixed waypoint routes per known structure (added 2026-08-07), fallback to generic heuristic in `StartClimbingMonument` if no authored route matches. Powerline tower route is complete through Ladder_3 + the plank zone; Ladder_4's final ~1.5m approach is a known, deliberately-parked gap (see 2026-08-08 session).
- `Plugin\LivingRust.Hooks.cs` — `OnPlayerDeath` (death handling + respawn scheduling), `RespawnSurvivor`, `TryFindOwnedBag`, `GiveStartingKit` (added 2026-08-08).
- `Plugin\LivingRust.Looting.cs` — task-driven looting (added 2026-08-08): `TaskType.LootForResources`/`Character.CurrentTask`, `/lr.debug.settask` scans a 50m radius (deliberately not monument-seeking), walks to and repeatedly `Hurt()`s containers (real damage, Phase A only — no swing animation yet, that's Phase B, deferred pending research into Rust's client-driven melee/animation system). Fills main AND belt (not just main) before stopping. Excludes junkpile_j's own containers (its loot sits inside a van model, not external like other junkpile letters) and, after 4 consecutive walk/line-of-sight failures, poisons a 20m radius around wherever the survivor got stuck so the next pick comes from further away (`LootTaskState`) — added after a live report of a survivor thrashing near junkpile_j's obstructive scatter geometry while trying to reach *other* nearby containers, not junkpile_j's own loot. `StartWalking` (`Commands.cs`) gained a real per-tick-displacement stuck detector and an `onFailed` callback as part of this work — general navigation fix, not looting-specific.
- `Plugin\LivingRust.Persistence.cs` — `CaptureAllLiveState`/`RestoreSpawnedSurvivors`, full inventory+position+health capture/restore across plugin reload or server restart; also wakes natively-reloaded sleeping bots (`EndSleeping()` + `SendNetworkUpdateImmediate()`) and treats a live world entity as authoritative over stale `Spawned`/`State` persisted values (added 2026-08-08, hardened same day - see [[project-livingrust-persistence-hardening]]).
- `Plugin\LivingRust.Main.cs` — plugin lifecycle: `Init`/`OnServerInitialized` (calls `RestoreSpawnedSurvivors`)/`Unload` (calls `CaptureAllLiveState`, no longer auto-despawns bots)/`OnServerSave` (also calls `CaptureAllLiveState` + `SaveCharacters`, so the roster stays in sync with Rust's own native saves even when the process gets hard-killed without a clean Unload).
- `Models\Character.cs` — persistent identity; `BotId` (permanent userID, issued once by `CharacterManager`, starts at 5,000,000 as of 2026-08-08 - see [[project-livingrust-persistence-hardening]]) is the key field making blueprints/build-privilege/respawn-at-bag all work correctly across a bot's deaths. `State` (`CharacterState` enum) gates `OnPlayerDeath`/respawn eligibility - only ever written in 3 places (constructor default Alive, `OnPlayerDeath`→Dead, `RespawnSurvivor`→Alive prior to the 2026-08-08 fix), so any code path that brings a character back into the world must explicitly set it back to `Alive`.
- Live test server files under `Rust\server\`; log at `Rust\server\LivingRust_log.txt` (own `Console.WriteLine`-based logger never reaches a readable file — always use Carbon's `Puts()`). Roster save file: `Rust\server\LivingRust\world.json`.
- Not a git repo (no `.git` as of 2026-08-07) — no commit history to check, only the dated session files.
- User's dev-restart workflow: runs the in-game `save` console command, then closes the server window directly (a hard kill, not a graceful Carbon `Unload`) — `OnServerSave` exists specifically to keep the roster valid across that workflow.
- Known, not-yet-actioned separate issue: `LivingRustEngine.Start()` auto-creates new "population" characters via `PopulationManager.GetRequiredSurvivors` on every single boot if under some target count - refills some empty characters on every boot regardless of wipes. `/lr.debug.despawnall` (rewritten 2026-08-08) now does a genuine clean-slate wipe of `CharacterManager`/`SurvivorManager`/`world.json` plus a live-world sweep for any `BasePlayer` in LivingRust's own BotId ranges (5,000,000+, plus legacy 1000-1099) regardless of tracking — untracks *before* killing, since killing a still-tracked survivor fires `OnPlayerDeath` like a real death and schedules an unwanted respawn otherwise (confirmed via live test).

**Why this matters:** the project moves fast across sessions with a lot of engine-reverse-engineering nuance (physics layers, NavMesh quirks, `SendModelState` requirements, Rust internals with no source access).
