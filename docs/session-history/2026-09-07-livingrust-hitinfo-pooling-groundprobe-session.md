# 2026-09-07 — Post-update compile fixes, HitInfo pooling bug, ground-probe root cause, aggression tuning

Picked up from the 2026-09-01 session (see that file for everything shipped then: terrain-climb-check scoping, duck-animation decoupling, life-stall watchdog, resource-node poisoning, rock-drop gate, animal hunting feature, etc). Today opened with the plugin **not actually running at all** due to an external Rust/Carbon update, then moved through a long chain of live-trace-driven root-causing. Multiple 200-250 bot batches spawned and traced throughout.

## Critical: Rust/Carbon update broke compilation entirely
Carbon had self-updated to 2.0.259.0 (2026-09-03) and Rust to a 09/04 build since last session - both newer than what the plugin was built against. The plugin failed to load on the live server (Carbon's own compiler, not just local `dotnet build`, which was silently using stale cached assembly references until a fresh build finally surfaced the same errors). Four real breaking changes, all fixed:
1. `RustNavMeshAgent.destination`/`RustNavMeshPath.corners[...]`/`RustNavMeshAgent.velocity` now return `Rust.Ai.Gen2.Nav.NavVector3` instead of `UnityEngine.Vector3` - fixed with explicit `(Vector3)` casts at the three call sites (LivingRust.Commands.cs, LivingRust.Debug.cs).
2. `BaseEntity.SetFlag` was removed - `SetFlagLocal` (same signature) is the replacement, confirmed via ilspycmd decompile of the live `Assembly-CSharp.dll`. Fixed the one call site (P17 burst-mode toggle, LivingRust.Combat.cs).

**Takeaway for next session:** always assume a Rust/Carbon update may have landed between sessions - run a fresh `dotnet build` first thing, don't trust that yesterday's clean build still holds.

## The "Cannon"/Bradley red herring - fully resolved
A live trace showed 90-97% of all deaths logged as `died (Cannon)`, scattered with zero position clustering across the whole map (one survivor died "Cannon" three times in 5 minutes, 1000+ units apart each time) - physically impossible for real Bradley. Root-caused via ilspycmd decompile of `DamageTypeList.GetMajorityDamageType()`: when a death has an all-zero damage-type array (no real damage ever recorded), the algorithm's `!(num2 < num)` comparison mechanically walks forward through every index and lands on the LAST valid enum entry - which happens to be `Cannon` (second-to-last, right before the `LAST` sentinel). Pure coincidental artifact, unrelated to Bradley.

Traced further and found the REAL cause of the all-zero data: `OnPlayerWound` (LivingRust.Hooks.cs) - the existing "force death instead of real Rust wounding" system (a 2026-08-11 design decision, confirmed still correct and NOT to be reverted per Lucas's explicit instruction this session) - defers `player.Die(info)` via `timer.Once(0f, ...)` to dodge a real recursion hazard. But `HitInfo` is one of Rust's own **pooled** objects; by the time the deferred call actually runs on the next tick, the original synchronous damage pipeline had already returned that same `info` to the pool for reuse elsewhere, silently clearing its fields. **Fix**: capture the real `Initiator`/`HitPositionWorld`/a cloned `DamageTypeList` synchronously inside `OnPlayerWound` (before returning control to Rust's pipeline), and build a genuinely independent `new HitInfo()` for the deferred `Die()` call. **Verified**: 100% of deaths before the fix showed "UNRECORDED" (renamed from the old misleading "Cannon" label as part of this fix); 0% after, across every subsequent trace this session. Real causes now show correctly: Bite, Slash, Bullet, Blunt, Stab, Arrow.

## Bot-vs-bot aggression was still preventing bases from ever being built
Traced `RowdyMiner` (furthest-progressed bot in a mid-session trace) getting repeatedly hunted by 3 different armed bots while gathering, finally killed mid-gather - the exact pattern behind zero bases ever completing despite dozens of bots reaching base-gather phase across multiple long sessions. Two fixes, both explicit Lucas asks:
1. **Target-side protection** (LivingRust.Combat.cs, `TryStartBotOnSightCombat`) - mirrors the existing rock-only attacker carve-out, applied to the defender: an armed bot no longer proactively targets another bot that has nothing worth fighting over (no real ranged weapon, no real non-rock melee tool). Reactive self-defense unaffected. Verified live: zero gear-0/unarmed bots appeared as engagement targets anywhere in the post-fix trace.
2. **`BotVsBotAggressionGracePeriodSeconds` raised 900s -> 1800s** (15 -> 30 minutes), same server-uptime-based mechanism from last session.

**Parked, explicitly not built yet** (Lucas: "don't fix straight away, wait until we verify logs"): extend the same 30-minute grace period to real-player on-sight aggression too (currently bots attack real players completely unconditionally when not looting, with zero grace period at all - confirmed this has been the design since 2026-08-14, predating any of this session's work, when Lucas was surprised bots were attacking him mid-noclip).

## Self-healing was almost entirely unreachable - fixed
`TryUseMedicalItemIfHurt` had exactly one caller in the whole project - a probabilistic combat-tactical-retreat roll, meaning a hurt survivor doing anything else (looting, gathering, just walking) had zero path to ever bandage itself. Two fixes (both explicit Lucas spec: "a bot realistically should want to be at 100 health all the time... passively set, not forcefully done"):
1. Unconditional fire-and-forget call at the top of `ContinueLootTask` (every cycle, every phase) - no-ops instantly if healthy/on cooldown/nothing to heal with.
2. New `TryPursueBandageSupplyIfHurt` - health<80 AND zero real heal items triggers the existing (already-built, checklist-only) `TryPursueBandageGoal`, now reachable post-checklist too.
3. Extended `TryGatherCraftIngredient`'s cloth case with a genuine "kill animals and farm them for cloth" fallback (`TryPursueAnimalHuntForCloth`, reuses last session's hunt-and-harvest pipeline, no bow requirement) alongside the existing hemp-collectible search - benefits primitive-checklist bandage crafting too, not just this new path.

## The rock-formation relocation bug - two false starts, then the real root cause found
Lucas reported bots ending up 20-30m in the air atop rock formations, "physically impossible." Chain of fixes across the session:
1. **First attempt**: traced to `TryForceRelocateIgnoringCollision` (the life-stall watchdog's last-resort fallback, built 2026-09-01) doing a raw `TryFindGroundBelow` raycast with zero validation. Made it reuse `TryValidateEmergencyTeleportCandidate` (the existing safe, validated first-tier check) with a wider elevation tolerance. **This introduced a severe regression**: 270 distinct bots got stuck in an unresolved rescue loop, ZERO successful relocations, because `TryCalculatePath` (real path connectivity FROM the survivor's current position) is structurally impossible to satisfy for a survivor that's only in this fallback because normal pathing already doesn't work from where it's standing.
2. **Second attempt**: added a `requireRealPath: false` parameter to skip just the connectivity check for this specific wide-search case. Still 0% success, still ~900+ failures.
3. **Added real diagnostics** (a `failureReason` out-param threading up through the whole validation chain) rather than guessing further - this is what actually found it: **98.5% of failures were "no real ground found within the probe window,"** not the elevation cap or connectivity.
4. **The real root cause**: `TryFindGroundBelow`'s own doc comment (NavigationManager.cs) admits its `searchHeight`/`searchDistance` parameters are **completely non-functional** ("no longer honoured separately... kept as parameters so existing call sites don't need touching") - a 2026-08-15 internal rework silently deprecated them, but every caller that predates that rework (including this session's new code) had no way to know. The function only ever does a small, fixed-range consensus probe right at whatever origin point it's given. Passing `candidate + Vector3.up * 20f` as that origin (believing `searchHeight=20f` would make it search a real 20m window) meant every probe was floating 20m above the candidate's real ground level, only ever finding something if a real object happened to reach up that high - which is EXACTLY why the original bug landed bots on rock formations specifically (tall enough to register) and why the "fixed" version found almost nothing (ordinary flat terrain isn't 20m tall). **Real fix**: seed a sane ground-level Y guess from the real terrain heightmap (`TerrainMeta.HeightMap.GetHeight`, the same proven pattern `TryFindRandomInlandSite` already uses) before ever calling the probe, so it has legitimate ground to confirm near instead of searching blind from an arbitrary height. **Verified**: force-relocate success went from 0/900+ to 42/305 (~14%) in the first minute after deploy - a real, substantial improvement, though not 100% (remaining failures are plausibly genuine dense-terrain/no-real-nearby-ground cases, not a further logic bug).

## New admin tooling
`/lr.tp.bot <name or partial name>` (chat + console) - case-insensitive substring match against `Character.Alias`, teleports directly to a live survivor regardless of whether it's currently flagged "stuck." Sibling to the existing `/lr.tp.stuck`.

## Diagnosed, not yet fixed
- **`/lr.tp.stuck` has a blind spot**: `_stuckSince` (what it reads) is only set/cleared by `EscalateStuckRecovery`'s own tier-0-to-completion window - once that ladder gives up and calls its own `onFailed`, the flag clears even if the survivor is still stuck via the SEPARATE life-stall watchdog picking it up independently 30s later. A genuinely-stuck bot whose original recovery ladder already exhausted itself becomes invisible to `/lr.tp.stuck` even though it's still stuck. Fix would be having `RescueGenuinelyStalledSurvivor` also call `MarkStuck`/keep it alive while its own relocation attempts keep failing. Not built this session - only diagnosed.
- **Force-relocate still fails ~86% of the time** even after the real fix - worth watching whether this settles into "acceptable, just genuinely hard terrain" or needs a further look (e.g., trying more than 8 random attempts, or a smarter directional search instead of pure random angles).
- **Real-player grace period** (parked, see above) - extend the 30-minute bot-vs-bot window to also cover proactive real-player engagement.

## Explicit design decisions confirmed/corrected this session
- Bots do NOT go into Rust's real wounded state at all (explicit 2026-08-11 decision, confirmed still correct by Lucas today after I initially misdiagnosed the death-cause bug as a wounded/bleedout issue - it was never that, always the HitInfo pooling bug above).
- Real-player on-sight aggression has always been unconditional/probabilistic since 2026-08-14 - not a bug, not new this session, just something Lucas hadn't fully registered until bots kept attacking him mid-noclip. `/lr.debug.noplayercombat on` is the existing testing toggle.
- Monument gear-score weighting (`GetTierWeights`) - Lucas wants this REMOVED entirely from destination-selection (any bot should be willing to roll any monument regardless of gear, matching real player behavior), keeping gear/progression gating ONLY on the actual keycard-puzzle content. **Explicitly parked, not built** - "note it down for later."
- En-route resource gathering during long inland walks (stop at 1-2 stone/tree nodes along the way, reusing the existing en-route-loot-scan pattern already proven for containers) - confirmed feasible, **explicitly parked, not built**.

## Repo/tooling notes
- `dotnet build` can silently pass against stale cached assembly references even when the live server's actual managed DLLs have changed - don't trust a clean local build alone after any suspected external update; check the live Carbon log for its own compile result too.
- ilspycmd (10.1.1.8388, update available but unused) is available on PATH and was essential this session for decompiling `DamageTypeList`, `HitInfo`, `BaseEntity`, and `NavigationManager`'s own `TryFindGroundBelow` - worth reaching for it earlier next time a "why does this real Rust API behave unexpectedly" question comes up, rather than guessing first.
