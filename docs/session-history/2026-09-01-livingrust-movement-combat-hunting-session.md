# 2026-09-01 — Movement/combat root-causing, bot-vs-bot aggression tuning, animal hunting feature

Extremely long, continuous session (250→150→270+ bot live trace testing throughout). Summary below covers everything shipped, in rough chronological order, plus an explicit verification checklist for next session.

## Context carried in from before this session
- Persistence hardening (2026-08-08), melee combat system, "merciless game of Rust" aggression philosophy, rock-only PvP carve-out, launch_site avoid-zone scoping, checkpoint-audit cleanup (stale comment fix, dead `_tacticalActionUntilTime` field removed) — all pre-existing/confirmed working before today's changes began.

## Root-caused and fixed this session

1. **Rock-drop gate** ([LivingRust.Looting.cs](Plugin/LivingRust.Looting.cs) `DropRockIfUpgraded`) — was dropping the rock the instant a bot got ANY better `MeleeToolPriority` tool, including just one of hatchet/pickaxe, stranding it unable to gather the other resource type. Now requires BOTH a real hatchet-family and pickaxe-family tool before dropping (simplified from an earlier "nearby-resource-bootstrap" version per Lucas's explicit "keep their rock UNTIL they get a hatchet AND a pickaxe" spec).

2. **Resource-node poisoning** (new, LivingRust.ResourceGathering.cs) — a tree/ore node that gives a survivor ZERO real engagement (no hits landed) within `GatherEngagementTimeoutSeconds` (10s) now gets globally blacklisted for `ResourceNodePoisonDurationSeconds` (600s/10min) via `_poisonedResourceNodeUntil`, checked in every tree/ore candidate-selection predicate project-wide. Fixed the "bot idling next to a tree forever" retry-loop bug (root cause: `EscalateStuckRecovery`'s tree/ore stuck-detour branch retried the exact same node at a static low recovery tier on every failure, never escalating or trying anything different).

3. **Death-cleanup for base-less survivors** (LivingRust.Hooks.cs `OnPlayerDeath`) — `_hasRolledHomeSiteStrategy`/`_homeSiteTarget`/`_pursuingBaseGatherGoal`/`_rolledBaseDesign`/`_primitiveGoalRetryTime`/`_coastalProgressSnapshot`/`_ingredientSearchCooldownUntil` now reset on death **only if** `Character.Home == null` — a base-less bot that dies gets a genuine fresh inland/coastal re-roll next life instead of permanently skipping the roll (since `_hasRolledHomeSiteStrategy` is keyed by the persistent `Character.Id`, which survives respawn). A bot that already has a base is completely untouched by this (Lucas's explicit qualifier: don't reset base-having bots to scratch).

4. **THE major root-cause fix: `MaxClimbAboveTargetHeight` check scoping** ([Navigation/NavigationManager.cs](Navigation/NavigationManager.cs) `TryGetNextStep`) — this check compared every step's local ground height against the FAR FINAL destination's elevation (not a nearby waypoint). On any walk where start/destination differ meaningfully in elevation (any ordinary hillside route — extremely common terrain), nearly every early step got rejected as "would climb onto Terrain Xm above target," even though nothing was actually wrong — it's just what walking down a hill looks like partway through. This was THE dominant cause of the mass "blocked heading" spam and the "walking not running" visual symptom (bots stuck in tiny sidestep-shuffle loops making near-zero real progress). **Fix**: added `ClimbAboveTargetCheckRadius = 15f` — the check now only applies once genuinely close to the destination (preserving its real original purpose: catching a wrong-turn climb right at arrival, the "JitteryWolf ended up on a store countertop" bug it was built for). **Verified via live trace**: "would climb onto Terrain" dropped from 1106+ occurrences in a 70s window to 0, and to a legitimate close-range-only ~734 in a later ~11min/270-bot window (vs what would've been thousands at that scale pre-fix).

5. **Real-time-based local-step watchdog** (LivingRust.Commands.cs `LocalStepProgressWatchdogTripped`) — converted from an int tick-counter (`TicksSinceLocalStepProgress`) to a real `Time.realtimeSinceStartup`-based window (`LocalStepProgressWindowStartTime`). Root cause: the old counter only incremented once per CALL to the function, but call cadence varied wildly by caller (every tick for the plain unblocked-step site, only once per SUCCESSFUL sidestep — itself gated behind `SidestepAfterTicks`=5 — for the sidestep-rescue site), so the same nominal "10s" threshold actually represented ~5x longer real-world stall time for the sidestep path specifically. Now measures true elapsed time regardless of caller.

6. **New top-level "life stall" safety net** (LivingRust.Commands.cs, `StartLifeStallWatchdog`/`RunLifeStallWatchdog`/`RescueGenuinelyStalledSurvivor`) — a coarse, independent, survivor-level check (every 5s) watching real position (`LifeStallMinMoveDistance`=2m) and `CurrentTask` changes. If neither changes for `LifeStallTimeoutSeconds`=30s, treats the survivor as genuinely stuck regardless of WHY: poisons the surrounding area globally (`_globalStallZones`, `GlobalStallZoneRadius`=15m, `GlobalStallZoneDurationSeconds`=600s, wired into `IsInMonumentAvoidZone` so every existing candidate-filter call site respects it for free) and relocates via `TryEmergencyTeleport`, falling back to a raw ground-only `TryForceRelocateIgnoringCollision` (30-80m away) if even that fails to find a valid landing spot. Registered in `OnServerInitialized`/`Unload` alongside `StartOnSightDetection`.

7. **Duck/crouch animation decoupled from step-up detection** (LivingRust.Commands.cs `ApplyMovementStep`) — `npc.modelState.ducked`/`ducking` used to be tied to `steppingUp` (`StepResult.SteppedUp`, which fires for ANY >5cm rise per `NavigationManager.cs`'s `stepUpHeight > 0.05f` threshold). On ordinary outdoor terrain this fires almost every tick during a real run, meaning bots were rendered in a near-constant crouch-walk (a real, distinct Rust animation state) while actually moving at full RunSpeed — visually reading as a "halfway between walk and sprint" jog, exactly matching Lucas's live report once bots were actually covering ground again post-fix #4. Now always `false` — `steppingUp` wasn't used for anything else inside the function (actual step height was already resolved into `nextStep.y` upstream).

8. **Walk timeout raised 200s → 600s** (LivingRust.Commands.cs `StartWalking` default `maxSeconds`) — root cause behind bots sticking on the shoreline: only 4 of 166 inland-site rolls in one trace window ever actually arrived (57 explicitly gave up — "couldn't reach its inland site"). The flat 200s default couldn't geometrically cover a genuinely distant inland site (often 1500-3000m) even at a dead sprint with zero obstruction (RunSpeed 5.5m/s × 200s ≈ 1100m max). 600s covers ~3300m unobstructed. The two callers with their own explicit shorter overrides (collectible walks, en-route loot detours) are untouched.

## New behavior/design changes (explicit Lucas requests, not bug fixes)

9. **Bot-vs-bot 15-minute aggression grace period** (LivingRust.Combat.cs `BotVsBotAggressionGracePeriodSeconds`=900f, gates `TryStartBotOnSightCombat` only) — root cause of a live finding: a 150-bot, 8-minute trace showed 369 melee engagements across 95 bots, ZERO checklist completions, ZERO base-gather transitions — any bot with even a single real weapon would proactively chain-engage every weaker nearby bot indefinitely (the armed-vs-unarmed "OUTMATCHES" check is an absolute yes/no, so raising `OutmatchGearScoreAdvantage` would NOT have fixed this — confirmed and explained to Lucas before implementing the cooldown instead). Uses `Time.realtimeSinceStartup` (real process uptime, survives plugin hot-reloads, only resets on a genuine server restart) matching Lucas's own "day 3 of the server, different story" framing. Reactive self-defense (bot-vs-player AND bot-vs-bot-if-actually-hit) is completely unaffected — only proactive bot-vs-bot seeking is gated. Debug override: `/lr.debug.skipbotgraceperiod [on|off]` (chat + console) for testing without a real server restart.

10. **`/lr.debug.spawnmany` 20% inland-spawn fraction** (LivingRust.Debug.cs `SpawnManyInlandFraction`=20) — reuses `TryFindRandomInlandSite` (already-validated: real ground, not underwater, not inside a monument no-build zone) to instantly place a fifth of a spawn batch inland rather than at a real beach spawn point, skipping the walk-there step entirely "to aid progression." Falls back to a normal beach spawn if the roll fails to find a valid site.

11. **Proactive animal hunting before base-build** (new, LivingRust.HomeSiteStrategy.cs `TryPursueAnimalHunt`/`StartAnimalHuntEngagement`/`StartHarvestingCorpse`) — **UNTESTED, needs live verification first thing next session.** Once a survivor is in `_pursuingBaseGatherGoal` (past checklist, gathering for a base) and owns a real bow/crossbow (`BowFamily`), searches up to 150m for the nearest huntable animal (Bear/Polarbear/Boar/Stag/Wolf2/Crocodile/Panther/Tiger — same 8 types already recognized by on-sight combat), walks to it, engages via the existing `StartCombat` ranged pipeline, polls for the kill (45s give-up), then harvests the corpse with a hatchet/skinning knife via a new `StartHarvestingCorpse` function that mirrors `StartGatheringResourceNode`'s real attack-based `DoAttackShared` pipeline but targets a `BaseCorpse` instead of a `ResourceEntity`. Capped at 5 kills per life AND a 15-minute phase window from the first hunt attempt (`AnimalHuntPhaseWindowSeconds`) — after either cap, falls straight through to normal base-gather priorities (hammer/planner/resource requirements), never blocking progress. Death-cleanup added for all three new dictionaries (base-less-only, same pattern as #3).

## Diagnosed but explicitly NOT fixed (by Lucas's own choice)
- Bots phasing/flying up to an admin's position while noclipping — Lucas said "don't worry about the latter" when this came up; root cause understood (phasing/melee-chase logic targets the live target position with no "target must be grounded" check) but left alone.
- Real-player on-sight proactive aggression (bots attack ANY nearby real player unconditionally if not looting, or probabilistically if looting) is NOT new — confirmed this has been the design since 2026-08-14, predating this whole session. Lucas was surprised by this; pointed him at the existing `/lr.debug.noplayercombat` toggle for testing without being attacked.

## Diagnosed, NOT yet fixed — carry into next session
- **`body would overlap solid geometry` is now the dominant block reason** (67% of all blocks in the last trace, 4626 occurrences/~11min/270 bots) — a genuine per-step volumetric collision check, not obviously miscalibrated the way the terrain-climb bug was. Overall stuck-bot percentage (~40%) hasn't dropped much since the terrain-climb fix, because this density-driven category took its place as bot count grew. Likely just genuine physical crowding (junkpiles, other bots, vehicles) at high population, not a single fixable logic bug — but worth a closer look if it's still dominant next session.
- **A hot air balloon and bikes are showing up suspiciously often** in block reasons (283 and 203 occurrences respectively in one trace) — `IsBlockedByHotAirBalloon` genuinely checks for a real `HotAirBalloon` component (not a name-substring false-positive), so this is very likely a REAL vehicle sitting/flying somewhere on the map that many bots are routing near repeatedly. Worth checking in-game whether there's a leftover balloon/bike parked from earlier testing.
- **Server memory footprint** — `RustDedicated.exe` was observed holding 16.4GB private memory / 4.3GB working set with a 270+ bot population (system has 31.8GB total RAM). This is disproportionately large for a test server and was the likely cause of a PC freeze + spurious EAC violation Lucas hit (resource exhaustion, not a plugin security issue — nothing in the code touches anything outside the Rust server process). Recommend restarting the server between heavy population tests, and not running the game client simultaneously with 200+ bot tests.
